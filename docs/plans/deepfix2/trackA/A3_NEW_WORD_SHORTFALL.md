## Leg (ii) — end-of-list: allocation = remainder, expected, with client/server parity

VERIFIED at both allocation sites: client `wordsRemaining = totalListWords - totalWordsIntroduced; newWordCount = computeCyclingAllocation(allocation.newWords, wordsRemaining, cyclingActive)` (/app/src/services/studyService.js:462-463) where the non-cycling branch is exactly `Math.min(allocationNewWords, wordsRemaining)` (studyService.js:155-159; cycling dead — CYCLING_ENABLED=false featureFlags.js:98, and R2-39 retired it, /app/docs/plans/deepfix2/02_TASK_LIST.md:158). Server parity in completeSession: `wordsRemaining = totalListWords - currentTwi` (foundation.js:1379), `serverNewWordCount = Math.min(allocNew, wordsRemaining)`, `wordsIntroduced = reviewOnlyDay ? 0 : Math.max(0, serverNewWordCount)` (foundation.js:1414-1415). So with 10-20 words left of a pace-larger allocation, the student gets exactly the remainder; the new-word test then presents ALL of them when the pool is smaller than testSize (`eligible.length <= testSize → return shuffleArray(eligible)`, studyAlgorithm.js:405-407) — a smaller test, by construction. At 0 remaining, the day is a legitimate review-only day that still advances (`isListComplete = wordsRemaining <= 0` foundation.js:1386, `listComplete` reason :1392, advance not held for list-end :1458-1461; client mirror comment studyService.js:1765-1779). **Verdict: produces David's symptom on the final intake day(s) and is expected remainder behavior, not a bug.** One corner: the non-cycling allocation can go NEGATIVE on over-introduction (deliberately unclamped for byte-equivalence — studyService.js:146-148; completion clamps at foundation.js:1415), which presents as premature "no new words" days when twi was ever over-advanced — the probe's end-of-list classifier (nwei = wordCount−1) also catches these.

## Leg (iii) — retake-pool shrinkage: REFUTED; no already-tested exclusion exists anywhere in the new-word retake flow

**Selection has no memory.** `selectTestWords(wordPool, testSize)` filters only still-retired MASTERED words (F01), shuffles, slices — no exclusion of previously tested words, no draw history (/app/src/utils/studyAlgorithm.js:391-411). For NEW-word pools the F01 filter is a no-op because `getNewWords` returns raw list words with no studyState/status attached (studyService.js:1197-1216; excludeRetiredMastered requires status === 'MASTERED', studyAlgorithm.js:372-388).

**The daily-flow pool is the full day allocation and never shrinks.** `navigateToTest` passes `wordPool = newWords` (the whole introduced set) for phase 'new' (/app/src/pages/DailySessionFlow.jsx:1233-1235); `buildTestConfig` draws `wordsToTest = selectTestWords(wordPool, effectiveTestSize)` AND carries the FULL pool as `originalWordPool` (/app/src/utils/testConfig.js:43-50).

**Retake paths, both verified:** (a) MCQ in-page retake: `handleRetake` for type 'new' re-draws `selectTestWords(originalWords, configuredTestSize)` (MCQTest.jsx:956-970) where PATH A set `originalWords = testConfig.originalWordPool` — the FULL pool (MCQTest.jsx:260). Each retake is a fresh random testSize-draw from the full 100; membership varies, pool size constant. (b) Typed in-page retake: same call (TypedTest.jsx:1233-1248) but PATH A set `originalWords = testConfig.wordsToTest.slice(0, MAX_TYPED_TEST_WORDS)` — the ALREADY-DRAWN set (TypedTest.jsx:299-301), so every Typed retake re-presents the SAME first-draw words reshuffled. (c) Flow-level re-entry after a fail: DailySessionFlow routes back to PHASES.NEW_WORDS (score < retakeThreshold, DailySessionFlow.jsx:1443-1453) and the next `navigateToTest` rebuilds the config — another fresh full-pool draw (DailySessionFlow.jsx:1246-1248). Failed new words feed the review STUDY queue only and are stripped from the review TEST pool (DailySessionFlow.jsx:1229-1235); queue tracking (`updateQueueTracking`, studyService.js:811-827) writes only `lastQueuedAt`/`queueAppearances`, whose sole readers are review-queue ORDERING (studyAlgorithm.js:296-310) and the post-test reset (studyService.js:780-782) — nothing feeds test-pool exclusion.

**Verdict: David's scenario (100 words, draw 30, fail 3×, 4th test from 10) is structurally impossible in this code — the 4th MCQ test draws 30 from the full 100; the 4th Typed test presents the same 30 as the 1st.** The pool also cannot shrink day-over-day from failing: `wordsIntroduced` credited at completion is the full allocation, independent of test draw or failures (foundation.js:1414-1415). Structural note (not a bug, feeds the redesign's composition work): with testSizeNew < pace, the untested majority (70 of 100) can complete the day untested — MCQ redraw makes coverage grow across retakes, Typed keeps it fixed at the first draw. Note testSizeNew default is 50 (studyAlgorithm.js:18); David's 30-of-100 premise requires a teacher-set `testSizeNew` below pace (assignment field, testConfig.js:30).
