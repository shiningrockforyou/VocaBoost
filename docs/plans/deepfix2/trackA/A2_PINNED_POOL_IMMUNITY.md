## Summary

A2 verdict: the absolute claim "a word-status change mid-day does not alter an in-progress review session" is REFUTED as stated, but a bounded version is certifiable. The day's review membership IS pinned (segment.wordIds, studyService.js:414-439) and an already-composed test/study deck is never mutated by external status writes within one continuous tab session — however (1) graduation ALWAYS re-reads live status at completion (studyService.js:1517,1524), so mid-day writes change what graduates; (2) every re-entry and every crash-restore path except the new-word-test one RE-COMPUTES the pool from live status (the pin is per-tab-volatile, never durably persisted); (3) the F01 still-retired filter drops externally-MASTERED words at every study-set rebuild, and an all-mastered pinned set collapses the day to auto-complete. For R2-10 specifically: a challenge-accept stamps status PASSED (db.js:2973-2982 live; foundation.js:2642-2647 server twin), and a PASSED flip is MEMBERSHIP-NEUTRAL in every live composition path — so the recommendation's "pool impact ≈ nil" premise is CONFIRMED in effect, though the true mechanism is tab-scoped pinning plus PASSED-flip neutrality, not durable pinning. One nonzero edge: accept on a meanwhile-MASTERED word overwrites it to PASSED = early un-retirement. Server day-advance reads no word status at all (foundation.js:1284-1690) and is fully immune; client graduation is unarbitrated — a duplicate already_completed completion re-runs graduation, bounded only by the live still-retired re-read. All claims are VERIFIED by direct code reading unless marked INFERRED.

## CERTIFIED STATEMENT (draft — activates R2-10; boundary conditions are part of the statement)

**In CURRENT code (flags as live: `LIST_SCOPED_RECON=true`, `SERVER_PROGRESS_WRITE=true`, `FORCED_PATHWAY=true`, `REENTRY_GUARD=true`, `RECOVERY_GUARD=true`, `SERVER_OVERRIDE=false` — src/config/featureFlags.js:47,77,218,194,230,135; `SERVER_COMPLETE_SESSION_ENABLED=true` — functions/foundation.js:44):**

Once a daily session is initialized in a tab, the day's review-word MEMBERSHIP is pinned as `segment.wordIds` (studyService.js:414-439) and carried ONLY by that tab's React state (DailySessionFlow.jsx:588), that tab's sessionStorage blob (DSF:1278-1292), and localStorage crash markers (src/utils/sessionRecovery.js:41-65). **Within one continuous tab session, a mid-day word-status change — by another tab, another class sharing the list, a teacher challenge-accept, or a CS write — can never ADD, SUBSTITUTE, or REORDER words in an already-composed review test, an in-progress study deck, or a retake draw.** The composed sample is frozen in memory and router state (DSF:1246, 1326-1331; testConfig.js:43-45; MCQTest.jsx:249-263) and question generation is a pure in-memory transform (MCQTest.jsx:210-240).

**The claim is REFUTED outside these bounds — three windows re-read live state:**

**B-1 GRADUATION (always live).** `graduateSegmentWords` re-resolves the pinned ids WITH FRESH STATUS at completion (studyService.js:1517) and drops still-retired MASTERED words (:1524, via studyAlgorithm.js:372-389). External writes between pin and completion therefore change WHICH and HOW MANY words graduate (count = floor(pinned size × score) capped at live-eligible, :1530-1537; random draw :1543-1545; MASTERED+21d write :1547-1563). Membership never grows — only the pinned ids are candidates — but eligibility inside them is live.

**B-2 STUDY-SET REBUILD POINTS (live status; membership still capped at the pin).** `buildReviewStudySet` = fresh `resolveSegmentWords` + F01 `excludeRetiredMastered` (DSF:509-527, filter :512-514). It runs at: init review-resume (DSF:611-643, call :615; a duplicate later block :835-846 is unreachable because :638 returns), `moveToReviewPhase` after the new test passes (DSF:1024-1050, from :1448), re-entry retake (DSF:1632-1653), and study-phase local recovery (DSF:1690-1702, intersected with saved ids :1697-1699). An externally-MASTERED word disappears from every screen built AFTER the write, and — because the review-test pool is the in-memory `reviewQueue` minus study-only new-FAILED (DSF:1232-1235) — from the subsequent test too. If the ENTIRE pinned set is mastered mid-day, the rebuild collapses to the all-mastered modal → `completeSession()` with reviewScore null → the day auto-completes with NO review test and NO graduation (DSF:617-623, 1039-1041, 1053-1055; graduation skipped because DSF:1561 requires a non-null reviewScore).

**B-3 RE-PIN POINTS (full recompute from live state).** The pin is NOT durable: the Firestore `session_states` doc stores no word ids (sessionService.js:38-48), so (i) every fresh DSF mount re-runs `initializeDailySession` and re-slices the segment off the LIVE unmastered pool (DSF:574-588; studyService.js:418-439; pool read :659-691; deterministic slicer studyAlgorithm.js:188-215) — identical output only if statuses, twi, and returnAt-expiries are unchanged; (ii) `returnMasteredWords` runs before every pin (DSF:571; studyService.js:1579-1605), so a rest expiring between two same-day inits changes the pool; (iii) crash-restore recompute-on-loss — see the dedicated section.

**Server completion is fully status-immune:** the `completeSession` callable reads lists, attempts, classes, and class_progress only — zero `study_states` reads (foundation.js:1284-1690; repo grep shows study_states in foundation.js only at reset :2094-2095 and challenge-accept :2643). Day-advance can never be altered by a word-status write. The corollary: graduation has NO server arbitration (client-side only — the sole live call site is studyService.js:2004-2015; DSF's own :1561-1570 is reachable only from the no-review path which passes a null reviewScore, :1055).

## Mechanism 1 — where the day queue is pinned

- **Pin creation:** `initializeDailySession` builds the segment from the live unmastered pool: `getUnmasteredPool` (studyService.js:418-419; impl :659-691 — introduced words position < twi, fresh study-state fetch :686, `excludeRetiredMastered` :688) → `computeUnmasteredSegmentIds` deterministic day-slice (:421-425; studyAlgorithm.js:188-215) → `REVIEW_STUDY_CAP` cap (:426-427) → `segment = { wordIds: cappedIds, startIndex, endIndex }` (:428-439). The comment at :414-417 states the design intent: "segment.wordIds is the pinned effective set used by study, test, AND graduation."
- **Pin carriers (all client-volatile):** React state (DSF:588); per-tab sessionStorage `dailySessionState` written at `navigateToTest` (DSF:1278-1292 — includes `sessionConfig` with segment AND the resolved `reviewQueue`) and at test-crash recovery (DSF:720-734); localStorage markers holding the new-test `wordPool` and study `studyQueue` ids (DSF:1300-1323; sessionRecovery.js:41-65). Durable Firestore `session_states` holds phase/scores/dismissed-ids only — NO word ids (sessionService.js:38-48).
- **Materializer preserves membership:** `resolveSegmentWords` prefers pinned wordIds (studyService.js:744-750); `getSegmentWordsByIds` re-attaches LIVE statuses but returns exactly the input ids in input order (:706-731) — status is refreshed, membership is not recomputed.
- **INFERRED (platform semantics):** sessionStorage survives reloads/same-tab navigation and dies with the tab; localStorage survives restarts. This is what makes the pin "one continuous tab session" scoped.

## Mechanism 2 — every mid-session status re-read (complete enumeration)

1. **Study-set build (F01 #1):** `buildReviewStudySet` → fresh `resolveSegmentWords` + `excludeRetiredMastered` (DSF:512-514) at the four entry points listed in B-2. This is the ONLY fresh Firestore status read between pin and submit on the happy path.
2. **Test composition (F01 #2 — the historical 'F01' chokepoint):** `selectTestWords` filters `excludeRetiredMastered(wordPool)` (studyAlgorithm.js:391-411, chokepoint comment :396-401), invoked from `buildTestConfig` (testConfig.js:43-45) at `navigateToTest` (DSF:1246). **CRITICAL NUANCE: this filter runs on the IN-MEMORY pool — no fresh Firestore read at compose time.** Its effective freshness = the last `buildReviewStudySet` run. On the "go back to study" return path the pool is restored VERBATIM from the sessionStorage blob (DSF:1352, 1367) — statuses as stale as the original `navigateToTest` — so an externally-MASTERED word survives F01 there and is still presented (consistent with pinning; inconsistent with a "still-retired filter at test build" reading).
3. **`selectReviewQueue`'s F01 backstop (studyAlgorithm.js:277-284, MASTERED drop :284) is DEAD in the live flow:** its only caller is `buildReviewQueue` (studyService.js:1230-1274) whose only caller is `getDebugSessionData` (studyService.js:1661+), used solely by the dev SegmentDebugPanel (src/components/dev/SegmentDebugPanel.jsx:51). The FAILED-priority bucketing (:296-353) therefore has NO effect on live composition — the live review test is a uniform random draw over the pinned pool.
4. **Graduation (the only OTHER fresh read):** studyService.js:1517 + :1524, as B-1.
5. **Standalone/PATH-C test build (fresh re-pin, not a re-read of an existing session):** MCQTest.jsx:341-358 / TypedTest.jsx:394-411 re-run `initializeDailySession` + `resolveSegmentWords` + `selectTestWords` — live everything. Live-session relevance: this is exactly the path the review-test crash recovery lands on.
6. **Status WRITES from inside the session (self-inflicted, for completeness):** `processTestResults` at submit overwrites status PASSED/FAILED for PRESENTED words, merge:true (studyService.js:763-799, status :775, merge :785), ordered attempt-write → processTestResults → completeSessionFromTest (MCQTest.jsx:779-790, 848; TypedTest.jsx:1038-1044); `updateQueueTracking` at study-finish is status-neutral (studyService.js:811-827; DSF:1189-1193); `initializeNewWordStates` touches only today's NEW words, which sit outside the pool bound position<twi (studyService.js:1121-1135, bound :669-672).
7. **Retakes re-read NOTHING:** new-word retake re-draws from the captured `originalWords` (MCQTest.jsx:956-970, draw :968; TypedTest.jsx:1244); review retake rewinds progress from the snapshot then re-navigates with the SAME `testConfig` — same `wordsToTest`, zero recomposition (MCQTest.jsx:1016-1042 → PATH A :249-263). Review attempts also always record `passed=true` in current code (MCQTest.jsx:581) — there is no review gate today; retakes are voluntary re-entry.

## Interleavings — dual-tab and second-class writes (compose→submit and beyond)

Word truth is CLASS-BLIND: `users/{uid}/study_states/{wordId}` (studyService.js:587, 772, 1553), while progress/segments are per class (`class_progress/{classId}_{listId}`, MCQTest.jsx:816-818). Two classes sharing one list share every word's status. Composed sequences below are INFERRED from individually VERIFIED steps (not executed):

- **Compose→submit window (the R2-10 window): IMMUNE.** A status write landing after `navigateToTest` cannot touch the frozen sample; the word is presented and graded regardless (no re-read exists between compose and grading).
- **Submit-time clobber:** tab A's `processTestResults` overwrites status on every PRESENTED word (merge) — a word class B graduated mid-test in class A comes out PASSED/FAILED, its `masteredAt/returnAt` left dangling but inert (`isRetiredMastered` requires status==='MASTERED', studyAlgorithm.js:372-377). The word is thereby EARLY-UNRETIRED and re-eligible for tab A's graduation (fresh 21-day clock possible, studyService.js:1547-1563).
- **Unpresented overlap words:** still MASTERED at tab A's completion → dropped from eligible (:1524) → tab A graduates FEWER words. Mid-day cross-class writes thus demonstrably alter graduation outcomes both directions.
- **Dual-tab duplicate completion re-runs graduation:** second submit of the same completed day returns `already_completed` from the server (foundation.js:1355-1364, mapping :1561-1566), which the client maps to a SUCCESS shape (studyService.js:1032-1038 — deliberately, as does `review_recorded` :1040-1052) → `completeSessionFromTest` falls through to graduation (:2004-2015). The second pass cannot re-graduate still-retired words (live re-read excludes them) but graduates ADDITIONAL eligible words up to its own floor(size×score) — i.e., the live re-read is what BOUNDS the damage; pinning does not. Genuine day-guard rejections and refusals DO skip graduation (studyService.js:1979-2002; foundation day_guard path studyService.js:1014-1030), and DSF's own handler lacks the dayGuardRejected guard but its graduation branch is unreachable with a review score (DSF:1549-1556 comment; :1055 sole call).
- **Same-class dual-tab pins agree** only while the pool is unchanged between the two inits (deterministic slicer); any interleaved graduation/returnAt-expiry shifts the second tab's slice (B-3).

## Crash-restore — the recompute-on-loss path (DSF:707-756, real site of the task's 'DSF ~:712-718')

Mid-TEST crash recovery (DSF:698-756):
- **Segment for GRADUATION:** the code explicitly preserves the ORIGINAL pinned segment from the prior sessionStorage blob when it survives — `recoveryConfig = { ...config, segment: prior.sessionConfig.segment }` (DSF:712-718, comment :707-711 naming the studied-set==graduated-set invariant). **On blob loss (tab closed → new tab; sessionStorage is per-tab) the catch falls back to the freshly RECOMPUTED config — the re-sliced live segment governs graduation. This is the recompute-on-loss: VERIFIED.**
- **Presented set, NEW test:** restored verbatim from the localStorage marker's `wordPool` (DSF:705, 739 'new' branch) — pinned across restarts.
- **Presented set, REVIEW test: RECOMPOSED FROM LIVE STATE.** DSF passes `wordPool: null` for review (:739) and no `testConfig`, so MCQTest lands on PATH C — a fresh `initializeDailySession` re-slice + `resolveSegmentWords` + `selectTestWords` (MCQTest.jsx:341-358). Saved answers are only INTERSECTED against the regenerated sample under RECOVERY_GUARD (MCQTest.jsx:409-427; the comment at :410-411 states it plainly: "MCQ regenerates its word sample per load"). A review test resumed after a crash is therefore NOT pinned — its presented set reflects live status, while its graduation can still use the older pin if the blob survived (a deliberate asymmetry).
- **Mid-STUDY crash recovery:** uses the freshly recomputed `sessionConfig.segment` (no preservation) + fresh `buildReviewStudySet`, intersected with the saved queue ids (DSF:1690-1702) — live status, membership ≤ (new pin ∩ saved ids).

## R2-10 activation — challenge-accept specifics and verdict on the deferred gate

- **The stamp:** accepting a challenge writes `status:'PASSED'` + `lastTestedAt` to the shared study_state — live path is the CLIENT leg since `SERVER_OVERRIDE=false` (db.js:2866-2870 routing, write :2973-2982; featureFlags.js:135); the server twin is foundation.js:2642-2647 (ledger's cited lines — VERIFIED accurate). The day-advance sub-leg is server-side under `SERVER_CHALLENGE_WRITE=true` (featureFlags.js:23).
- **Membership-neutrality of a PASSED flip:** the unmastered pool excludes ONLY still-retired MASTERED (studyService.js:683-690); FAILED/PASSED/NEVER_TESTED/NEEDS_CHECK are all pool members. Live composition is uniform random over the pinned pool (selectTestWords), and the FAILED-priority selector is dead code (section above). Therefore a FAILED→PASSED flip changes NO in-progress session and NO future day-queue membership — at most the dead debug-panel ordering.
- **The one nonzero edge:** accept on a word that was MASTERED between test and review (test graded → day completed → graduation ran → teacher accepts) overwrites MASTERED→PASSED = immediate early un-retirement; the word rejoins the pool at the next pin instead of after its 21-day rest (masteredAt/returnAt left dangling but inert per isRetiredMastered).
- **Verdict for David's R2-10 confirm:** the WSL recommendation's premise ("today's code already stamps status PASSED on accept... pool impact ≈ nil because day queues are pinned") is **CONFIRMED IN EFFECT but with a corrected mechanism**: in-progress sessions are protected by tab-scoped pinning (real, but volatile — not durable across re-entry), and future sessions are protected by the PASSED-flip's membership-neutrality, not by pinning. Under the redesign the protection strengthens to a persisted immutable day-queue record + compose-to-submit drift rule (10_ §2(1)) — the current-code gaps (B-1/B-3) are exactly what that record closes. Nothing found refutes "UPDATE labels on accepted challenge"; the mid-day label write is invisible to any composed presentation and touches only graduation-eligibility semantics that the redesign moves server-side anyway.
